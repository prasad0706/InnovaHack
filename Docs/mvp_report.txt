Why This Slice First
Everything downstream — Leak Score, Savings Simulator, Action Center, AI Insights — depends on getting clean, structured transactions out of a bank statement. If this layer is shaky, every other feature inherits the bug. Build and demo-proof this slice before touching UI polish elsewhere.

On the 'generic parser' decision
You chose the harder, more impressive path. Be deliberate about what 'generic' means: it should mean 'doesn't hardcode one bank's exact column names,' not 'handles every possible PDF layout ever produced.' Build it generic within the shape of a typical tabular bank statement (date, description, debit, credit, balance — in some order). A truly universal parser (scanned images, exotic layouts) is out of scope for 24 hours — see Section 17.

Password-Protected PDF Handling
Indian bank statements are commonly protected with a password derived from the account holder's own details — most often date of birth (DDMMYYYY) or the first few characters of name + DOB, sometimes PAN. Since you chose the user-types-it-in-the-UI approach, this is straightforward but needs clear error handling.
Flow
User uploads PDF.
Backend attempts to open it unprotected.
If it raises a decryption/password error, respond with HTTP 422 and a specific error code (e.g. PDF_PASSWORD_REQUIRED).
Frontend shows a password input, resubmits the same file with the password field populated.
Backend attempts pikepdf.open(..., password=...). Wrong password → 401 with PDF_PASSWORD_INCORRECT, distinct from step 3's error, so the UI can show 'wrong password' vs 'this file needs a password.'

Transaction Cleaning & Normalization
Whatever tier produced the rows, funnel everything into one normalized schema immediately (see Section 14). Cleaning steps, in order:
Parse dates into ISO format (handle DD/MM/YY, DD-MM-YYYY, DD Mon YYYY — build a small list of formats to try with dateutil.parser as a last resort).
Parse amounts: strip commas/currency symbols, convert to float, keep debit/credit as a signed or typed field (not both — pick one, be consistent).
Drop non-subscription-relevant rows: salary credits, interest credits, ATM withdrawals, cash deposits, NEFT/RTGS credits, refunds. Keep only debit-type transactions that look like recurring payments (UPI, card, auto-debit, standing instruction).
Drop duplicate rows (same date + amount + description appearing twice due to table extraction overlap across page boundaries — a real pdfplumber gotcha).

import statistics
def detect_price_increase(amounts: list[float], threshold_pct=5, threshold_abs=50): if len(amounts) < 2:
return None
baseline = statistics.median(amounts[:-1]) current = amounts[-1]
change = current - baseline
pct = (change / baseline) * 100 if baseline else 0
if change > threshold_abs or pct > threshold_pct: return {
"increased": True, "amount_change": round(change, 2),
"percent_change": round(pct, 1),
}
return {"increased": False}

Risks Specific to Your Choices
Being blunt, as requested: you picked the two hardest options (generic parser + password support) over the safer ones. That's a legitimate bet for impressiveness, but here's what it costs you:
Risk
Why it happens
Mitigation
Generic parser fails on a layout you didn't test
Indian bank statement layouts vary more than expected — merged cells, multi-line descriptions, inconsistent date formats across even the same bank's different account types
Tier 1 + Tier 2 fallback (Sections 7–8) is your safety net. Test against 3+ genuinely different layouts before demo day, not just one
Password decryption fails silently or throws an unhandled exception
pikepdf/pypdf raise different exception types depending on encryption algorithm (RC4-40, RC4-128, AES-128, AES-256)
Wrap decrypt logic in a broad try/except that maps any failure to PDF_PASSWORD_INCORRECT rather than crashing the endpoint
Time sunk into parser edge cases starves the frontend/demo polish
Generic parsing is a bottomless pit — there's always one more layout to handle
Hard time-box: Section 4's hour ranges are not suggestions. If Tier 1+2 works on your 4 test PDFs by hour 9, stop touching the parser

What to Explicitly Cut If Time Runs Out
If you're behind schedule by hour 14–16, cut in this order (least damaging to demo first):
OCR / scanned-PDF support — you were never building this; just make sure the error message is graceful (Section 15).
Regex fallback parser refinement — if Tier 1 (table extraction) works on your demo file, a rough fallback that only needs to not crash is acceptable.
Full 100-merchant dictionary — 20–25 merchants covering your demo file's transactions is enough; expand only if time remains.
Password-protected support — if decryption is fighting you past hour 6, demo with an unprotected file and mention protected-file support as 'in progress' rather than losing hours here. This is the one feature you could cut entirely and still have a coherent, complete demo.
Do NOT cut: the core table-extraction → cleaning → subscription detection → price increase chain. That chain is the entire point of this slice.
